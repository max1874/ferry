# 消息撤回

> [English](message-recall.md) | 简体中文

## 约定与验收 — 2026-11-01

Max 要求支持撤回已发送内容。Max 已确认：可信空间内任意已连接设备均可不限时间撤回任意文本、图片和文件，包括其他设备发送的消息和未记录发送身份的旧消息。设备名称和原发送身份不限制撤回权限，不引入账号或所有权系统。

核心读数是接收端时间线和原文件下载：接收端先收到内容，撤回后内容消失，原下载地址和已签发的下载票据返回 404。接收端重连、服务器重启后内容仍然不存在。正常发送、复制文本、预览图片及原字节下载继续可用。

有限验收清单：

1. 发送文本和文件；另一个身份收到并下载原始字节。
2. 取消撤回，内容保留；确认撤回，发送端和接收端都移除内容。
3. 读过后续消息后撤回旧消息；重连后补齐超过一页的撤回。
4. 其他已连接设备可以撤回，包括旧消息；已失效身份即使经过此前的认证也不能撤回。任意已连接设备重复请求幂等。
5. 迟到的轮询、发送响应和图片请求不能恢复内容；清除图片缓存，移除消息时关闭已打开的预览。
6. 使用相同存储重启，内容仍然不存在，中断的文件删除得到补完。真实客户端运行覆盖与构建、CI 分开报告。

撤回不能擦除已复制内容、已完成或正在进行的下载及备份。撤回记录仅保留消息 ID 和完成序号，消息正文和文件元数据删除。先持久化撤回意图，再删除文件；删除成功后才在同一事务内移除消息并分配撤回序号。文件删除失败时返回错误，保留消息和重试入口，不发布撤回；重复请求或重新打开存储会完成清理。

## 同步与升级边界

消息与撤回各有独立序号。客户端携带两个游标，先处理撤回再追加同页消息，在会话内记住已撤回 ID，并分别补齐两条分页流。消息游标只随获取到的页面前进，不随发送响应跳跃。仍使用现有前台轮询机制。

先升级服务器，再升级客户端。新版客户端仍能在旧服务器上读取和发送，但撤回会报错。旧客户端忽略新增撤回字段，已加载的内容可能保留到重连或重载，不能实现实时撤回。Web 随服务器更新；原生 App 更新仍需单独授权分发。

## 局部界面设计

仅改变消息行和撤回确认：复制或打开收到的内容，以及移除误发送内容。沿用导航、输入框、字体、颜色、间距与正常发送行为。在所有已连接设备上，Recall 是内容下方消息操作行里的可见垃圾桶图标，紧挨 Copy（布局及 2026-11-01 的决定见 [DESIGN.zh-Hans.md](../DESIGN.zh-Hans.md)）。请求中禁用并显示 Recalling…；失败时保留消息，通过现有错误区提示重试。撤空后显示现有空状态。删除消息不自动滚动到底部。

iOS 使用原生确认面板，其中 Recall 为破坏性按钮，另有 Cancel，参考 Apple [Action sheets](https://developer.apple.com/design/human-interface-guidelines/action-sheets#Best-practices) 中 Mail 丢弃草稿的例子：删除项用 destructive 角色，Cancel 取消。说明对所有设备生效及已保存副本的边界。使用可见入口，遵循 [Context menus](https://developer.apple.com/design/human-interface-guidelines/context-menus#Best-practices) 中上下文菜单操作也要出现在主界面的规则。不增加触感或导航结构；点击区域尺寸见 DESIGN.zh-Hans.md。Android 使用 Material 确认框；Web 使用浏览器确认框。
