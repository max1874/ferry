# Web 消息元信息的位置

> [English](message-metadata-placement.md) | 简体中文

## 范围与决策

- 需求（Max，2026-09-01）：“**Mac Web**11:16 AM 这种显示在气泡底下感觉有点不舒服”。
- 完成标准：Web 把设备身份和时间显示在对应气泡的正上方；当前设备的消息组仍然靠右，其他所有组仍然靠左。
- 不做：原生客户端、元信息内容、消息身份、API/schema，以及更大范围的时间线重设计。
- 深度：focused。预算：2 个生产文件、净增 3 行生产代码、无持久化机制；一个静态测试文件和这份证据说明。
- 决策：只把已有的元信息/正文 DOM 顺序和间距反过来。这样保留语义，也避免重复元信息，或者用 CSS 视觉重排导致与辅助技术的阅读顺序不一致。

## 冻结检查清单与证据

1. 文字和文件消息都先追加元信息、再追加正文 — 静态内嵌资源测试。
2. 元信息与气泡之间有 6 像素间距 — 静态 CSS 合约加浏览器矩形测量。
3. 当前设备/其他设备的左右归属不变 — 用两个已鉴权身份的真实 Chromium。
4. 桌面和 390×844 都没有横向溢出 — 真实 Chromium 几何测量。
5. push 前 Go/JS/仓库/diff 检查都通过；Mac mini 重建时不删除命名数据卷。

本地旅程：最终工作树，基线 `9def952`；当前设备/靠右的 `Mac Web` 元信息底边 93.20、正文顶边 99.20，其他设备/靠左的 `Other Mac` 为 182.89/188.89。在 390 px 下间距同样是 6 px，右侧气泡结束于 x=378，左侧开始于 x=68，溢出为 0。录制：`ferry-message-meta-above-local`（5 帧）。

## 作者对抗式评审

1. 耦合状态 — DOM 顺序和一个间距是唯一的 producer；`rg message-head|article.append` 列出了它们。
2. 失败路径 — 没有改动请求、异步或错误路径；这是纯展示层修正，不适用。
3. 未改动的消费者 — 重读了完整的渲染代码块、受影响的 CSS 和 Web 静态测试；文件和文字共用同一个包裹结构。
4. 合约面 — 没有 API/schema/存储改动；DOM 阅读顺序有意随视觉顺序一起改变。
5. 原始复现 — 浏览器文本和矩形测量显示元信息在两种气泡之前、之上。
6. 当前 HEAD 旅程 — 桌面和手机截图都在最后一次生产代码修改之后截取。
7. 机制区分 — `firstElementChild` 是 `message-head`，它的底边正好在正文顶边之前 6 px。
8. 回归扫描 — 候选风险是破坏左右对齐；当前设备结束于 x=1172/378，其他设备开始于 x=468/68。
9. 规模/边界 — 文字和文件共用同一个追加逻辑；空时间线没有受影响的元素；长内容换行不变。
10. 合约攻击 — 不适用；没有改动协议、策略、schema、鉴权或普遍性的外部声明。
11. 断言 producer — `is-current-device` 的产生方式不变，仍然只有一个严格布尔值的渲染 producer。
12. 被推翻的发现 — 不适用；没有推翻之前的发现。
13. 轮次上限 — 只有作者聚焦的一轮；按 Max 的长期决定不用 subagent，以运行中的浏览器和机器检查作为收口证据。
